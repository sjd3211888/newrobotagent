# Git 与交付规范

状态：有效 · 日期：2026-10-10 · 范围：全仓库 · 关联：ITER-001

## 分支与提交

`main` 保存经确认的基线；每轮使用 `feat/<slug>`、`fix/<slug>`、`docs/<slug>` 或 `chore/<slug>`。初始化先保存已有选型文档，再在 `chore/engineering-standards` 建立规范，不未经授权合并回 main。

开始前检查 `git status --short`；选择明确基线，不丢弃未知修改。单人工作可直接使用任务分支；确需隔离并行工作时再创建 worktree，不默认增加空工作区。

提交标题使用英文，以 `feat:`、`fix:`、`refactor:`、`docs:`、`test:`、`chore:` 开头，尽量不超过 72 字符。提交说明记录必要原因、关联迭代与验证，不能用标题替代验收报告。

小步提交应当有清晰职责，适用检查通过；显式暂存本轮文件，审查 cached diff。不使用 `git add -A` 将未知产物一并提交。已授权本地提交可自动完成，推送、合并和部署按明确授权执行。

## 依赖与配置

项目使用已固定、可复现的依赖版本和锁文件，禁止以浮动 main 作为交付基线。增加或升级核心框架、运行时、语言及存储时记录决策、兼容性和验证。

示例配置有字段说明、缺失时行为及校验方式；部署侧密钥和设备配置独立保存。发布不得覆盖已有设备配置。新增迁移须说明前后版本、失败处理和可恢复方式，不能默默修改线上数据。

## 交付与回滚

交付记录至少包含：源码提交、目标系统/架构、依赖和协议版本、构建命令、产物名称与 SHA-256、配置要求、检查证据、已知限制、启动方式与回滚步骤。

产物在 `dist`，检查缓存在 `build` 或 `.local`；Git 保存脚本和脱敏发布记录。云端和设备侧需要协调升级时列出版本兼容矩阵，不能发布只有半条链路可用的组合。

激活前核对活动任务、导航、播音、配置与可回滚版本。软件恢复与实际设备状态分开核对；重启不能作为物理任务已停止的证据。首次真实交付前补齐对应环境的部署与回滚说明。

规范变更、功能迁移和发布记录通过迭代编号关联；CI 平台在远端仓库确定后接入同一检查入口，本轮不虚构远端或部署地址。
